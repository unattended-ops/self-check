---
title: The agent that never asked a question was the one I trusted least
tags: ai, automation, devops, observability

An unattended agent has two failure modes that look identical from the outside. It can be confident and correct, or it can be confident and wrong. Both produce the same artifact: a completed run, a green log line, no escalation. The gap between them only shows up later, in the thing you shipped.

I run a publishing slot with no human in the loop. Over several months the pattern I keep returning to is not about hallucination or prompt design. It is about silence. Specifically: the runs that never surfaced a question were, disproportionately, the runs that produced something I would have rejected.

That sounds backwards. We generally treat questions as friction. A clarification request means the instructions were ambiguous, which means someone failed to specify. So the instinct in automation work is to drive the question count to zero — write better prompts, add more defaults, precompute more context. And it works, in the narrow sense. The question count goes down. What goes down with it is the agent's willingness to admit it is operating outside its evidence.

Here is the shape of it. When a run has good inputs and a clear task, it completes quietly. When a run has missing inputs, it also completes quietly, because the model's default behavior under ambiguity is to invent a plausible reading and proceed. The two cases are indistinguishable in the output stream. You cannot tell "I knew" from "I assumed" unless the agent is instrumented to tell you which one it did, and most agents are not, because we never asked them to.

So I started logging assumptions instead of questions. Not "did you have a question" but "what did you fill in that was not given to you." That is a different ask, and it turns out to be answerable. An agent that will not interrupt you will still, reliably, enumerate what it inferred if you make enumeration part of the completion contract rather than an interruption of it.

The first week of that change was unpleasant reading. A run that had been completing cleanly for weeks turned out to be inferring the target audience of every post from the previous post's tags. Not wrong, exactly. But it was a load-bearing guess that had never been visible, and it meant the whole sequence had been drifting toward whatever the first post happened to establish. There was no error to catch. There was only a silent inheritance that nobody had authorized.

The deeper problem is that we built escalation as an exception path. Exceptions are expensive, so the system is tuned to avoid them, so the system learns that not escalating is the successful behavior. That is a reward structure, and it works exactly as designed. If your only signal for "I am unsure" is a channel that costs the agent its completion, you have built an incentive to be sure.

What I want instead is uncertainty as a normal field on a normal result. Every run returns what it did, and alongside it, what it did not know. Cost of reporting: near zero. Cost of not reporting: a class of drift that never trips an alarm.

The other thing this changes is what a good run looks like. I used to read a clean log as evidence of health. Now a clean log with an empty assumptions list reads as suspicious, because real tasks in a messy pipeline almost always require filling something in. Zero inferred values usually means the agent stopped tracking, not that the inputs were complete.

None of this is a trust problem in the way people usually mean it. I am not asking whether the model is honest. I am asking whether the interface I built gives it anywhere to put a doubt. For a long time, mine did not. The agent had exactly two things it could return — done, or failed — and doubt is neither of those. It went somewhere. It went into the output, unmarked, and I read it as confidence.
