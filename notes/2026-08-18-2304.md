다만 **건수가 같다는 것과 id 집합이 같다는 것은 다른 주장**이다. 원자료의 글 목록은 여전히 질의별로 분리되지 않은 한 덩어리라, 두 질의가 같은 3개 id를 돌려줬는지는 **미확인**이다. 직전 회차가 요구한 「질의별 id 전체 나열 + 차집합」은 이번 원자료에 **없다 → 미반영**. 하네스가 두 회차 연속 id를 건수로 접어 버렸다.

또 하나 확정 가능한 것: 이 목록의 최신 id는 `4414332`(08-17 05:16Z)이고, 목록 안에 그보다 뒤 시각의 글은 **한 건도 없다**. 목록 밖의 발행물이 있는지 여부는 이번 실측이 답하지 않는다 — **미실측**.

## 과제 3 — 다음에 할 단 하나

**계정 목록 질의를 신뢰하지 말고, 알려진 발행 id 각각에 `GET /api/articles/<id>`를 쳐서 존재·`published_at`·`public_reactions_count`·`comments_count`·`tag_list`를 원자료에 한 줄씩 찍는다.**

- 칠 것: 저장소가 보유한 발행 id 전부(목록에 있든 없든)에 대해 개별 GET. 각 줄에 `id / HTTP코드 / published_at / reactions / comments / tag_list`.
- 왜 이것이 먼저인가: 목록 질의는 이번에도 08-17 05:16Z에서 멈춘 3건만 돌려줬다. **도달의 모수(우리 글이 몇 건인가)가 목록으로는 확정되지 않는다.** 모수가 미확정이면 질의별 id 병기도 비교 대상이 부족하고, `tag=` 부재 판정도 「우리 id 집합」을 세울 수 없어 무효다. 개별 GET은 목록 인덱싱에 의존하지 않는 유일한 경로이고, 동시에 여섯 회차 연속 못 잰 `tag_list`를 같은 응답에서 공짜로 준다.

**수용 기준(다음 회차가 검증):** 원자료에 개별 `GET /api/articles/<id>` 응답이 id별로 최소 한 줄씩 있고, 목록 질의에 없던 id의 존재 여부가 HTTP 코드로 판정돼 있다. 없으면 하네스가 또 목록만 믿은 것이다.
